Setting Up Embedded EWM in S/4HANA: A Step-by-Step Architecture Walkthrough

A practical embedded EWM setup in S/4HANA: warehouse number, ERP mapping, warehouse structure, delivery integration, an end-to-end test and the errors you will hit.

Most embedded EWM projects stall in the first two weeks. The cause is rarely the warehouse design. It is usually the plumbing: a warehouse number that exists in EWM but is not tied to an ERP plant and storage location, or deliveries that never reach the warehouse. Setting up embedded EWM in S/4HANA is mostly about doing a short list of steps in the correct order.

This guide walks through that order. You will define the warehouse number, connect it to ERP, build a minimal warehouse structure, configure delivery integration, and run an inbound and outbound test. You will also get a table of the errors that usually appear and how to fix them. Where the older ECC/CIF-based setup differs from S/4HANA, or embedded differs from decentralized EWM, I say so. I have not copied exact IMG node names where they vary by release, so search the IMG for the quoted node names if your menu looks different.

⚡ Key takeaways
  • Embedded EWM runs in the same S/4HANA system, so there is no CIF and the ERP material master is used directly.
  • The warehouse number must be defined in EWM and connected to an ERP plant and storage location; this step makes the storage location EWM-managed.
  • Build a minimal structure first: storage types including GR and GI staging, sections and a few bins, then test.
  • Deliveries are the integration point: map ERP delivery types to EWM document types and watch queues with SMQ1/SMQ2.
  • Test inbound and outbound end to end and compare ERP stock in MMBE with EWM stock in /SCWM/MON.
  • Never delete queue entries or table data to fix errors; fix the cause and reprocess.

01What embedded EWM actually means

In embedded EWM, the EWM application runs inside the same S/4HANA system and client as MM, SD and FI. The EWM objects use the /SCWM/ and /SCDL/ namespaces, and they sit next to the classic ERP objects. There is no separate SCM server and no CIF to move master data across.

This changes three things you will notice immediately:

  • Material master: EWM reads the ERP material master directly. You only add warehouse-specific data with /SCWM/MAT1. See the material master views guide for the fields that matter.
  • Business partners: Plants, vendors and customers must exist as business partners, because EWM documents use partner IDs. Vendor and customer BPs come from CVI synchronisation, covered in the business partner guide.
  • Deliveries: The ERP delivery is the leading document. EWM creates its own warehouse-side delivery (inbound delivery or outbound delivery order) from it.
ECC vs S/4HANA: In ECC, EWM could only run as a separate SCM system, which meant CIF, a separate database and qRFC monitoring between two systems. In S/4HANA you can choose embedded or decentralized. If you are still deciding, read the embedded vs decentralized decision matrix first. Also check your licence: basic warehouse functions come with S/4HANA, but advanced EWM functions need the separate EWM licence.

Keep a small naming sheet before you start: ERP plant, storage location, ERP warehouse number, EWM warehouse number, and the BP IDs. Using the same 4-character warehouse number on both sides makes tracing documents much easier. It is a convention I recommend, not something the system forces on you.

03Step 1: Define the EWM warehouse number

The warehouse number is the top-level object. Every storage type, bin, queue, process type and stock record hangs below it.

  1. Go to SPRO > SCM Extended Warehouse Management > Extended Warehouse Management > Master Data > Define Warehouse Number. The data is stored in /SCWM/T300.
  2. Create the warehouse number, for example EW01, and give it a description.
  3. Assign the supply chain unit / business partner that represents the warehouse.
  4. Save, then open the related warehouse-number control settings and set the defaults for your warehouse, such as the unit of measure for weight and volume.

A common point of confusion: the old thin version of this article said the ERP warehouse number is mapped 1:1 to the EWM number. In practice they are two separate configuration objects that you connect in the next step. The 1:1 pattern is a good convention, but it is not automatic.

Do not create warehouse numbers casually in a shared development client. Warehouse numbers are hard to delete once documents, bins or stock exist against them. Agree the number first and transport it from a single client.

04Step 2: Connect the warehouse to ERP plant and storage location

This is the step that turns an isolated EWM warehouse into an integrated one. It has an ERP-side part and an EWM-side part.

PartWhat you doWhere (search the IMG if the path differs)
ERP sideDefine the ERP warehouse number (Logistics Execution) and assign it to plant and storage location. The assignment is stored in T320.SPRO > Enterprise Structure > Definition / Assignment > Logistics Execution
EWM sideMap the ERP warehouse number and the storage location to the EWM warehouse numberSPRO > SCM Extended Warehouse Management > Interfaces > ERP Integration > General Settings (nodes named like 'Map Warehouse Numbers from ERP System to EWM' and 'Map Storage Locations from ERP System to EWM')
PlantMake sure the plant has a business partner and a locationBP and the ERP integration settings

After this, a storage location assigned to the EWM warehouse is 'EWM-managed'. Stock in that location is no longer managed by ERP bin-level data. ERP keeps the quantity at storage location level, and EWM owns the bin-level detail.

Split storage locations by purpose from day one. A typical set is one EWM-managed location for normal stock and a separate ERP-only location for items that should stay outside the warehouse, such as consumables. Changing the assignment after go-live means a stock migration.

05Step 3: Build the warehouse structure

A minimal but realistic structure is enough to test the integration. You can refine it later. The full theory of each object is in the warehouse structure guide, so here I only show the build order and sample values.

  1. Define the storage types, including the staging types for goods receipt and goods issue, and set their roles.
  2. Define storage sections.
  3. Define storage bin types and activity areas if you plan to use them for picking or putaway.
  4. Create bins with /SCWM/LS01 for a few bins, or use the maintenance transaction /SCWM/LS10 and the bin-creation options in your release for bulk creation.
  5. Define the door and yard objects only if you need inbound/outbound dock handling. See the yard management guide.

Bins are stored in /SCWM/LAGP. If you ever need to check whether a bin exists, a quick look at that table settles the question.

I have deliberately left out the transaction /SCWM/LS01N that appears in older material. The create transaction I use is /SCWM/LS01. If your system offers a different mass-creation entry point, use it and confirm in your own release.

06Step 4: Configure delivery integration and process control

With structure in place, you tell the system how ERP deliveries become warehouse documents, and how the warehouse then moves goods.

Delivery mapping

Under the ERP Integration and delivery processing nodes in the IMG, map the ERP delivery types and item categories to EWM document types and item types. Standard EWM values are usually INB for the inbound delivery and OUTB for the outbound delivery order, with default item types for each. Start from the standard values and copy them only when you need a different behaviour.

Process control

  • Warehouse process types: They decide the movement logic (putaway, picking, posting changes). Read the warehouse process types guide.
  • Storage control: Use the process-oriented (POSC) or layout-oriented (LOSC) approach to route stock through staging, counting or packing. See POSC vs LOSC.
  • Determinations: Warehouse process type determination, putaway strategy and stock removal strategy need entries for your storage types. Without them, warehouse task creation fails.
  • Product master: Use /SCWM/MAT1 to maintain warehouse data and assign storage type search sequences.

How the delivery flows

When you create an inbound delivery with VL31N or VL01NO, or an outbound delivery with VL01N, ERP checks whether the storage location is EWM-managed. If it is, a warehouse request is created in the same system. EWM then builds its own delivery from it. The data is stored in the /SCDL/DB_PROCH_I and /SCDL/DB_PROCI_I tables for inbound documents. Communication stays within one system, but queue-based processing can still be involved. Use SMQ1 and SMQ2 if a document seems stuck.

Interview angle: 'How is embedded EWM different from decentralized in terms of integration?' A strong answer: no CIF, direct use of ERP master data, delivery-based integration within one system, and the point that goods movements update ERP stock through goods movement postings from EWM, not a separate interface server. Mention that you still monitor queues.

07Step 5: Run an end-to-end test

Test the cheapest scenario first: a standard purchase order, inbound, putaway, and then a sales order, picking and goods issue. For the purchasing steps, see the purchase order cycle guide.

Inbound

  1. Create a PO with ME21N for a material with warehouse data, using the EWM-managed storage location.
  2. Create the inbound delivery in ERP (VL31N for an ASN, or VL01NO against the PO).
  3. Open /SCWM/PRDI and find the same delivery on the EWM side. Check the status and the document type.
  4. Unload, create handling units if needed (/SCWM/ADHU), and post goods receipt from /SCWM/PRDI.
  5. Create and confirm the putaway warehouse task (/SCWM/TO_CONF or via RF with /SCWM/RFUI).
  6. Check that the stock appears in /SCWM/MON and that ERP shows the quantity in the storage location in MMBE.

Outbound

  1. Create a sales order and an outbound delivery with VL01N.
  2. Open /SCWM/PRDO to see the outbound delivery order.
  3. Create the warehouse tasks, directly or through a wave (wave management).
  4. Confirm picks, pack if needed and post goods issue from /SCWM/PRDO.
  5. Verify the goods issue in the ERP delivery, with the document flow, and the stock reduction in MMBE.
Check the open and confirmed warehouse task tables, /SCWM/ORDIM_O and /SCWM/ORDIM_C, and the stock table /SCWM/QUAN when debugging. They show you what the system believes, which is not always what the screen shows. The full cross-module picture is in the end-to-end logistics guide.

08Troubleshooting: common errors and fixes

Message wording differs by release, so I describe the symptom rather than quoting exact text. The cause and fix are what matter.

SymptomLikely causeFix
ERP delivery created, but no document in /SCWM/PRDI or /SCWM/PRDOStorage location is not assigned to the EWM warehouse, or the delivery type is not mappedCheck T320 and the IMG mapping of storage location and document types
Delivery stuck in a queueqRFC queue blocked by an earlier errorOpen SMQ1/SMQ2, read the error, fix the cause, then reprocess
Product not maintained for warehouseNo warehouse-specific product dataMaintain it in /SCWM/MAT1
No storage type found during putawayNo storage type search sequence or putaway control entryMaintain the search sequence and determination on the product and in the IMG
Business partner missing for plant, vendor or customerCVI sync or plant BP not createdCreate or sync the BP in BP and rerun CVI
Storage bin does not existBin not created, or wrong storage typeCheck /SCWM/LS03 or table /SCWM/LAGP
User cannot log on to RF or desktop transactions for the warehouseNo warehouse assignment for the userMaintain it in /SCWM/USER and check the authorisation roles
Do not clear queue entries or delete entries from the tables to 'get things moving'. You will create a mismatch between ERP and EWM stock that is painful to repair. Fix the cause and reprocess.

09Interview questions on this topic

  1. What is the sequence of steps to set up embedded EWM? Prerequisites (BP, logical system), EWM warehouse number, ERP warehouse number and plant/storage location assignment, mapping to EWM, warehouse structure, product data, delivery and process configuration, then testing.
  2. What does an EWM-managed storage location mean? The location is assigned to an EWM warehouse. ERP keeps stock at location level, and EWM holds bin-level stock.
  3. Where do you check why an ERP delivery has not reached EWM? The storage location assignment, the document type mapping, the queues, and then the warehouse request/delivery on the EWM side.
  4. How is the product master handled in embedded EWM? Directly from the ERP material master, with warehouse-specific data in /SCWM/MAT1.
Interviewers like scenario questions: 'Goods receipt is posted in EWM but ERP stock is not updated. What do you check?' Walk through the goods movement posting, any blocked queues, and the storage location assignment. For more, use the top 25 EWM interview questions.

If you want hands-on practice, build this setup yourself on an S/4HANA sandbox. Doing the steps once teaches more than reading about them.

?Frequently asked questions

Is a separate server needed for embedded EWM in S/4HANA?

No. Embedded EWM runs in the same S/4HANA system and client. There is no separate SCM server and no CIF for master data. You do need the right licence for advanced EWM functions.

Do the ERP and EWM warehouse numbers have to be the same?

No, they are separate configuration objects connected through mapping settings. Using the same 4-character number on both sides is a useful convention that makes tracing easier, but it is not enforced.

Which T-code do I use to create storage bins in EWM?

Use /SCWM/LS01 to create a bin, /SCWM/LS02 to change it and /SCWM/LS03 to display it. /SCWM/LS10 is used for bin maintenance. Check your release for the bulk-creation options.

How do I check whether an ERP delivery reached EWM?

Open /SCWM/PRDI for inbound or /SCWM/PRDO for outbound and search by the ERP delivery number. If nothing appears, check the storage location assignment, the document type mapping and the queues in SMQ1/SMQ2.

Do I need the CIF for embedded EWM?

No. The CIF is used in ECC to move master data to a separate SCM system. In embedded EWM the material master and business partners are used directly from the same system.

Can I switch from embedded to decentralized EWM later?

It is possible but it is a migration project, not a configuration change. Stock, open documents and master data all have to be moved. Decide early using the decision matrix.

Which tables help me debug warehouse stock and tasks?

Use /SCWM/QUAN for stock quants, /SCWM/ORDIM_O and /SCWM/ORDIM_C for open and confirmed warehouse tasks, /SCWM/LAGP for bins, and /SCDL/DB_PROCH_I with /SCDL/DB_PROCI_I for inbound delivery data.
